# Research Execution Model

Status: current
Owner: mmPRISM coordinator
Authority scope: Cross-workspace research terms, stage identities, and the end-to-end paper pipeline.
Last reviewed: 2026-08-12

## Purpose

This page connects manuscript terms to executable project stages. It defines what an artifact means and which
workspace owns its production. Tensor details remain in the [tensor contracts](../20_CONTRACTS/TENSOR_CONTRACTS.md),
while current progress and commands remain in the owning workspace Authority.

An artifact name, directory name, or historical checkpoint label is not provenance. A formal artifact carries a
source manifest, split, producer configuration/checkpoint, coordinate frame and units where applicable, checksums,
and validation status.

## Canonical Terms

| Term | Canonical meaning | Must not mean |
|---|---|---|
| `visual pose` | A pose estimated from RGB/image input, including native RTMW3D output and its canonical projection. | Manually measured 3D ground truth or a radar-derived result. |
| `cam-pose` | A selected, versioned visual-pose product accepted for a named semantic or simulation experiment. It remains a pseudo-label unless independent ground-truth evidence exists. | Any array found under a legacy `poses/` directory. |
| `pose target` | The declared supervision target for one reconstruction run, with source, transform, units and coordinate-frame identity. | An automatically metric or physically calibrated target. |
| `synthetic radar signal` | Complex FMCW samples generated by one declared simulator protocol from pose, point, or mesh input. | Measured radar data or a manuscript-equivalent simulator by default. |
| `synthetic radar cube` | A synthetic signal processed into a declared `[T,D,R,A,E]` power-cube protocol. | A real calibrated cube or proof of synthetic-to-real fidelity. |
| `mmw-pose` | A pose predicted by an accepted OmniHand/CubeNet checkpoint from a radar-domain input. It is always qualified as synthetic-domain or real-domain. | The cam-pose used to generate a simulated input. |
| `synthetic-domain mmw-pose` | OmniHand prediction from a declared synthetic radar signal/cube. | Real-radar reconstruction evidence. |
| `real-domain mmw-pose` | OmniHand prediction from accepted measured-radar input. | Camera annotation or simulated reconstruction. |
| `radar feature` | A frame-aligned feature exported by a declared radar/CubeNet producer checkpoint and bound to source, split, sample, frame and mask identities. | A path-inferred sibling array, fabricated zero tensor, or unbound internal activation. |
| `pose confidence` | A versioned per-joint reliability value with a declared producer and interpretation. | A universal physical uncertainty estimate. |

Use `camera pose` only as prose for `cam-pose`; use `predicted mmWave-pose` only when the producer and input domain
are explicit. In particular, `cam-pose -> simulator` does not directly produce `mmw-pose`: it produces synthetic
radar, from which OmniHand may predict synthetic-domain `mmw-pose`.

## Model Names And Roles

| Name | Role in the rebuilt project |
|---|---|
| RTMW3D | Optional visual-pose estimator that produces native pose/scores before the selected cam-pose transform and QC. |
| Simulator/processor | Produces a separately identified synthetic radar protocol and power cube; it is not a learned pose model. |
| CubeNet | Radar-cube spatial encoder used inside the reconstruction path; its frame features require an explicit export contract before reuse. |
| OmniHand | The pose-reconstruction train/evaluate surface that consumes radar cubes and produces pose predictions, metrics and checkpoint-bound features. |
| WaveLLM | The geometry-guided mT5 translation surface consuming an explicit pose-only or pose-plus-radar-feature delivery. |

Historical code may use these names differently. A historical replay records that difference instead of silently
mapping an old label onto the canonical role.

## End-To-End Stage Model

| Stage | Transformation | Owning workspace | Required handoff or gate |
|---|---|---|---|
| `S0` visual source | RGB/image sequence + text -> source manifest | `data_rebuild` or archived source workspace | Immutable source identity, caption identity and eligible split inputs. |
| `S1` cam-pose | source frames -> native visual pose/scores -> selected cam-pose | `data_rebuild` | Versioned annotation, QC/failure report, units and coordinate-frame statement. |
| `S2` synthetic radar | selected cam-pose -> synthetic signal -> synthetic cube | `data_rebuild` | Named simulator/configuration, numerical checks, manifest and split-bound delivery. |
| `S3` reconstruction | radar cube -> OmniHand checkpoint -> predicted mmw-pose and frame feature | `omnihand_training` | Formal run receipt, pose metrics, sample predictions and checkpoint-bound export. |
| `S4` translation control | accepted pose/feature sequence -> WaveLLM -> text | `wavellm_training` | Explicit input mode, aligned identities, accepted initialization, predictions and frozen metrics. |
| `S5` real adaptation | measured radar + reference target -> matched sim2real adaptation/evaluation | `data_rebuild`, `omnihand_training`, `wavellm_training` | Real acquisition/calibration identity, participant-disjoint split and equal-budget comparison. |
| `S6` paper promotion | frozen run evidence -> manuscript/response claim | `paper_revision` | Evidence-registry trace from data and split through checkpoint, predictions, metrics and display item. |

The current CSL-Daily controlled route is:

```text
CSL-Daily RGB + caption
-> selected RTMW3D-derived cam-pose
-> separately labelled skeleton-simulated radar cube
-> OmniHand synthetic-domain mmw-pose + checkpoint-bound frame feature
-> WaveLLM controlled translation matrix
```

The translation matrix keeps three questions separate:

```text
cam-pose -> pose-only WaveLLM                         semantic control
predicted synthetic-domain mmw-pose -> pose-only     reconstruction degradation
same predicted pose + matched radar feature          incremental fusion value
```

These are synthetic controls. They do not close real-radar fidelity, new-participant, orientation, occlusion, or
sim2real reviewer claims. Those require `S5` on accepted real data.

## Stage Handoff Rule

A stage may start a formal consumer run only after its producer delivery identifies:

```text
producer workspace and commit
immutable manifest/delivery location and hash
split assignment hash
configuration and model/checkpoint identity
tensor protocol, units and coordinate frame
validation status and known claim limitations
```

Fast fixtures and in-sample diagnostics may skip a formal cross-workspace delivery only when their run and output
are explicitly labelled engineering or diagnostic evidence. They cannot populate paper comparison tables.
